# Comprehensive Rules

- `MagicCompRules.txt` — the official text, fetched by the Reference data workflow from the URL in `SOURCE.txt`. To move to a new CR release, change that URL.
- `rules.json` — the parsed rules (rule number → text, examples, parent/children) plus the glossary.
- `TRACE.md` — which rules the engine and the compiler implement, which are tested, and which are checked in play. Generated by `pnpm rules:trace`; don't edit by hand.
- `PINNED.json` — the text of each cited rule when it was last looked at (see below).

## Citing rules in code

- Write `CR 117.3a` next to the code that implements that rule, one number per `CR`.
- Name tests after the rule they check: `it('CR 704.5a: a player at 0 life loses', …)`. The CR's own "Example:" paragraphs make good test cases.
- Mention rules that aren't implemented yet as `rule 613` (no `CR`), so the trace stays honest.
- `pnpm rules:check` (run in CI) fails if a citation names a rule that doesn't exist. This is how renumbering in a new CR release gets caught.

## When the rules change

- `PINNED.json` holds the text of every cited rule as it read when it was first cited or last looked at (`pnpm rules:trace` adds new ones; it never moves an old one).
- When a new CR release rewords a cited rule, `pnpm rules:check` fails and prints the old text, the new text and every place that cites it. Read the rule against that code, change what it changes, then `pnpm rules:pin` (all changed rules, or `pnpm rules:pin 704.5j`) to say it has been looked at.
- `pnpm rules:diff <older rules.json>` lists what a release adds, removes and rewords: a new set's keywords are the added rules in 701 and 702. `pnpm rules:keywords` then regenerates the keyword definitions the compiler reads.

## Rules as properties

`packages/engine/scripts/lib/rule-checks.ts` states rules as things that are true whenever a player has priority ("No creature on the battlefield has toughness 0 or less", CR 704.5f), each with its number. Random games and the card sandbox check them after every action, whatever the cards did. Such an entry doesn't say how the engine brings the rule about, so it catches the engine being wrong. A rule that changes is one entry to change. The trace lists them as "checked in play".

An entry is only worth what it can catch: `packages/engine/test/rule-checks.test.ts` holds, for each one, a state made by hand that breaks its rule, and fails for an entry that has none. The exceptions cards make ("You can't lose the game", an Aura on a card in a graveyard) are tested there too.
